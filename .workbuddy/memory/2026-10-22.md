### 改动（4 文件，cl /Zs /W4 x64+x86 双配置 0 error 0 warning）
- `renderdoc/os/win32/win32_process.cpp`
  - 新增 `InjectDLLViaContext()`：把挂起线程 RIP 指向本地生成的小 stub
    - x64 79 B：7 push 保存易失寄存器 → `mov r11,rsp` → `and rsp,-16` → `sub rsp,20` → `mov rcx,path` → `mov rax,LoadLibraryW` → `call rax` → `mov rsp,r11` → pop 回去 → `mov byte[rip+disp],1`(完成标志) → `jmp [rip+0]` 回原入口
    - x86 19 B：`pushad` / `push path` / `mov eax,LLW` / `call eax` / `popad` / 写标志 / `jmp rel32`
    - 写完 stub 后 poll 内存标志（最多 20s）；远程块**故意不 free**（避免线程还在 stub 里时 use-after-free）
    - 失败自动回退 CreateRemoteThread
  - `InjectDLL(hProcess, libName, hSuspendedThread=NULL)`
  - `InjectIntoProcess(..., void *hSuspendedThread)`，`LaunchAndInjectIntoProcess` 传 `pi.hThread`
- `renderdoc/os/os_specific.h` / `posix_process.cpp`：`InjectIntoProcess` 加可选 `void*` 参数（ABI 兼容，posix 忽略）
- `renderdoc/os/win32/sys_win32_hooks.cpp`
  - 子进程注入传 `lpProcessInformation->hThread` → 走无远程线程路径
  - `PatchChildCommandLine()` + 4 个 W hook（CreateProcessW / API110 / API111 / API112）：
    环境变量 `TCM_CHILD_ARGS` 的内容会**追加到每个被注入子进程的命令行**，解决 `-krqlv=hd` 不依赖壳转发
  - `IsSkipInjectTarget()` ACE/CrashSight 黑名单

## 01:42 第一版 hijack 注入把壳搞崩了 → 换成 Early Bird APC

用户重编译后实测（`RenderDoc_2026.10.22_01.37.08.log` + `RenderDoc_app_2026.10.22_01.37.55.log`）：

```
01:37:26 Injecting renderdoc into process 57856
01:37:26 Injected ... via thread context, no remote thread created     ← 新路径生效
01:37:26 WER 1000: Wuthering Waves.exe 0xc0000005 模块 unknown 偏移 0x00007fff59de80c0
01:37:55 第二次同样：WER 1000 模块 ntdll.dll 偏移 0xc3ab6
```
- 两次都没有 `Got remote handshake`、没有 `Got a new child process`、没有 CreateProcessW 拦截 → 壳注入后立刻 AV 崩溃，根本没拉 Client
- 结论：**「把挂起线程 RIP 指到 stub 直接调 LoadLibraryW」这个做法在 CREATE_SUSPENDED 的初始线程上是错的** —— 初始线程 context 还在 `LdrInitializeThunk` 里，loader 未完成初始化就 LoadLibraryW，直接在 ntdll/映射区炸

### 改为 Early Bird APC 注入
- `InjectDLLViaAPC()`：VirtualAllocEx 写 DLL 路径 → `QueueUserAPC((PAPCFUNC)LoadLibraryW, hThread, remoteMem)` → ResumeThread → 轮询 `FindRemoteDLL`（最长 10s，顺带查 GetExitCodeProcess）
- APC 由 ntdll 在 loader 初始化完成后、exe 入口点之前投递 ⇒ loader 状态合法，且 DllMain 装钩子发生在目标执行第一条指令之前
- 依然完全不创建远程线程；失败回退 CreateRemoteThread
- 删掉了 128B stub / 完成标志 / 上下文改写那一整套（不需要了）
- 因为 APC 会让目标立刻开跑，`INTERNAL_SetCaptureOptions` 可能晚到，所以 `ShouldInject` 增加 `TCM_FORCE_CHILD_INJECT=1` 旁路（A/W 两个重载都加了），保证壳→Client 那一跳不依赖选项到达时机

### 编译验证
cl /Zs /W4，x64 + x86 双配置，`win32_process.cpp` / `sys_win32_hooks.cpp` 均 0 error 0 warning（唯一 error 是 215 行 `RENDERDOC_SetDebugLogFile` 找不到标识符，HEAD 里就是这样，缺的是 vcxproj 内部 define）。

## 01:10 「launcher.exe 挂上就自己退了」原因

用户报：`C:\Wuthering Waves\launcher.exe` 用 RenderDoc 拉起，挂上就自己退。

结论：**它是 bootstrap，秒退是设计行为，不是崩**。
- `C:\Wuthering Waves\launcher.exe` 569544 B，native（无 CLR），加壳、无明文串；与 `3.0.1.0\launcher.exe` 同尺寸同文件
- 真正常驻的 UI 是 `C:\Wuthering Waves\3.0.1.0\launcher_main.exe`（563912 B，只有版本目录里有）
- 00:55–00:58 的 WER 里**没有** launcher.exe 的 1000/1001 → 不是被我们的 DLL 搞崩
- 历史一致：19:11、00:56、02:37 每次注 launcher.exe 都是 1 秒内 CONNRESET；而 02:37 注 `launcher_main.exe` handshake OK
- ⇒ 启动链：`launcher.exe`（bootstrap，秒退）→ `3.0.1.0\launcher_main.exe`（UI，常驻）→ `Wuthering Waves.exe`（壳）→ `Client-Win64-Shipping.exe`
