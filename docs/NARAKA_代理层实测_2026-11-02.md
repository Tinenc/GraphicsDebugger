## 1. 做了什么

把 `dxgi.dll` / `d3d11.dll` / `d3d12.dll` 三个代理放进 `F:\Naraka\program\`，
让游戏自己加载（详见 [`tools/proxy/README.md`](../tools/proxy/README.md)）。

## 3. 但保护识别了部署

按 `docs/DF_AUTHORIZED_CAPTURE_RESEARCH.md` 的边界，到此为止，不换姿势重试、
不做文件隐藏/伪装。记录 `unsupported-protected`。

## 4. 保留的部分

**核心侧的 D3D12 factory 桥接保留**，它完全在 `TinecmaTool.dll` 内部，
不需要在游戏目录放任何文件：

- `TINECMATOOL_CreateDXGIFactory` / `1` / `2`（`dxgi_hooks.cpp`）
- `TINECMATOOL_D3D12CreateDevice`（`d3d12_hooks.cpp`）
- `TINECMATOOL_D3D11CreateDevice` / `...AndSwapChain`（`d3d11_hooks.cpp`）
- 三条 create 路径按 System32 全路径解析真实函数（避免自递归）
- `g_SkipGraphicsDriverHooks`：代理宿主跳过 IAT 改写。对 Naraka 本体由 exe 名命中，
  这一条在 VMProtect 环境里本来就是必要的

代理源码（`tools/proxy/`）与测试保留：它是上述桥接的唯一验证手段，
且未来若出现不落在游戏目录的加载路径，可以直接复用。

## 5. 两个操作性发现（下次别再踩）

### 5.1 提权启动 → 游戏根本不起

从高完整性（提权）会话 `Start-Process` 拉起 `StartGame.exe`：`NeacClient` 会起，
但 `NarakaBladepoint.exe` 永不出现，`Player.log` 不更新。
同一条路径经 `explorer.exe`（中等完整性）拉起则正常进游戏。

### 5.2 通用转发器的参数个数必须是"最宽"的那个

第一版实机运行崩了：

```
NarakaBladepoint.exe  crash 0xC0000005
  in d3d11.dll at 0033:793ec321        (System32\d3d11.dll + 0xAC321)
  stack: D3D11On12CreateDevice
```

`Player.log` 的上下文：`Forcing GfxDevice: Direct3D 12` → `d3d12: loaded!` →
`aftermath enable shader debug info` → `Crash!!!`。是 NVIDIA Aftermath 在 D3D12
设备创建后立刻建 D3D11On12 设备。

`D3D11On12CreateDevice` 有 **10 个参数**，而当时通用转发器只声明了 6 个：
前 4 个走寄存器没问题，第 5、6 个还接得住，第 7–10 个是被调用方从栈上读的垃圾，
于是真 d3d11 里解引用崩溃。x64 下**多传**参数无害（被调用方不弹栈），**少传**致命。

修复：通用转发器统一为 12 个指针宽度参数（三张表里最宽的是
`D3D11CreateDeviceAndSwapChain` 的 11，且它是显式实现的）。
回归用例：`proxy_fixture` 在 D3D12 模式下真实调用一次 `D3D11On12CreateDevice`，
断言 `hr=0x00000000` —— 这个用例在修复前必然崩。

## 6. 之后又试了注入（2026-11-02 18:14 / 18:16）：成功注入，但包装不了

代理路线被封之后，试了唯一不碰安装目录的路线：注入渲染进程。两次实测，结论是
**注入本身可行且不被检测，但 IAT 钩子在这游戏上抓不到设备创建**。

### 6.1 先修掉一个我自己的 bug

`win32_libentry.cpp` 原本按进程名直接跳过图形 IAT 钩子：

```cpp
if(f == "narakabladepoint.exe" || envIsSet) g_SkipGraphicsDriverHooks = true;
```

那个名字判断是给代理路线写的，结果把注入路线一并废掉——注进去核心因为进程名就
注册不了任何钩子。改成只看 `TCM_SKIP_GRAPHICS_IAT`（代理会自己置位），单一来源。

### 6.2 第一次：慢了一步

| 事件 | 时刻 |
|---|---|
| 渲染进程启动 | 18:14:30 |
| 核心加载并注册钩子 | 18:14:40（**晚 10 秒**）|
| `sl.common.dll` 的 IAT 装好 | 18:14:43 |

当时 bat 用 `ping` + 每轮起一次 `tasklist` 轮询，光发现进程就花了 10 秒。设备大约在
渲染进程后 14 秒创建，钩子是踩着设备创建装好的，没抢到。改造为
`tools/naraka/wait-and-inject.ps1`：单进程 100ms 紧轮询，发现即注入。

### 6.3 第二次：抢到了，但钩子一次都没命中

| 事件 | 时刻 |
|---|---|

抢到窗口了，结果仍然为零：

| 指标 | 值 |
|---|---|
| `Graphics IAT hook installed` | 16 |
| `Graphics function resolved` | **0** |
| `api=D3D11CreateDevice` / `AndroidSwapChain` | **0** |

16 个钩子全落在第三方模块上（`fidelityfx_*` / `opencv_world490` / `GPUINFO` /
`sl.common` / `d3d11on12` / `libxess_fg` / `nvwgf2umx`），而真正做设备创建的
`UnityPlayer_LVB.dll` **只钩上了 `dxgi.dll!CreateDXGIFactory`，它的
`kernel32!GetProcAddress` 槽位根本没出现在日志里**——即 VMProtect 保护的解析路径
绕开了 IAT。这就是 10-24 §7 记录的那堵墙，现在在注入场景下再次确认。

### 6.4 这次实验的两个正面结论

1. **注入不被检测**：DLL 加载、16 个 IAT 写入、游戏正常跑完，没有提示、没有崩溃记录
   （`Crashes` 目录只有 17:20 那次修复前的）。也就是说"注入本身"不是被封的原因。
2. **卡点是解析路径，不是时间、不是权限**。所以再调注入时机没有意义。

### 6.5 改导出表（2026-11-02 18:2x 起）：不碰代码页的变体

原先判断"只剩 inline hook，代价太大"。后来换了个更温和的角度：**不改函数的机器码，
只改模块导出表里那一条 RVA**。

原因很直接——IAT 钩不住，是因为调用方解析函数的路径不经过我们改的槽位。但不管它怎么
解析，最后都要读 `d3d12.dll` 的 `AddressOfFunctions[ordinal]`。改那一条，比改函数
前几个字节浅得多：

- 不写任何现有指令，只在**节间对齐空隙**（section padding，本来就是 0）里放 12 字节跳板
  `mov rax, imm64 ; jmp rax`
- 跳板在模块自己的镜像内，所以新 RVA 仍是合法的小值（RVA 只能向模块基址以上偏移，
  跳板放在我们 DLL 里通常超出 4GB 范围）
- 只 `VirtualProtect` 那 12 字节和导出表项 4 字节，写完立刻恢复原保护
- 反作弊完整性校验通常盯着代码页，这里代码页一个字节都没动

实现见 `renderdoc/os/win32/win32_hook.cpp` 的 `LibraryHooks::RedirectExport()`，
由三处 `RegisterHooks()` 在 IAT 注册完之后调用，覆盖
`d3d12!D3D12CreateDevice`、`d3d11!D3D11CreateDevice{,AndSwapChain}`、
`dxgi!CreateDXGIFactory{,1,2}`。

**一个必须同时处理的连锁反应**：导出改掉之后，`GetProcAddress(d3d12, "D3D12CreateDevice")`
返回的就是我们的钩子。钩子再去"找真实函数"就会调回自己，无限递归——和代理那次的症状
一模一样。所以重定向时把原始 RVA 对应的地址缓存下来（`GetExportOriginal()`），三处钩子
一律先查缓存，再退回 `HookedFunction`，最后才 `GetProcAddress`。

同时补上"伪装"那一半：注入的核心在 `RegisterHooks()` 完成后把自己从 PEB 三条模块链表里
摘掉（`win32_libentry.cpp`），环境变量 `TCM_NO_PEB_UNLINK=1` 可关闭以便调试。

代理路线会自动跳过这一切：代理会设 `TCM_SKIP_GRAPHICS_IAT=1`，`RegisterHooks()` 提前
返回，既不改导出表也不摘 PEB。

### 6.6 附带发现：后端被启动器改成了 D3D11

`ExtraVars.unityargs` 现在是 ` -force-d3d11`（10-24 时是 ` -force-d3d12`），
`tempdx12.txt` 仍在但未生效，本次会话 `Player.log` 为
`Forcing GfxDevice: Direct3D 11` / `Direct3D 11.0 [level 11.1]`。
