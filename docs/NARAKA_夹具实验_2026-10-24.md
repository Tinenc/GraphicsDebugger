# Naraka 夹具实验：D3D11 抓帧失败机制复现（2026-10-24）

> 目的：2026-10-24 01:14 直启 `NarakaBladepoint.exe` 时，钩子全部安装成功，但整场
> `Graphics function resolved` 计数为 **0**，设备从未进入包装。本次用自建夹具隔离变量，
> 确认到底是哪一环漏掉的。
>
> 结论先行：**漏点已复现并可稳定重现**——只要目标自己遍历 PE 导出表取
> `D3D11CreateDevice`（不经过 IAT、不经过 `GetProcAddress`），我们的钩子就完全看不到。
> 这正是 VMProtect 加固过的 `UnityPlayer.dll` 的行为。

## 1. 为什么需要夹具

Naraka 客户端有三个变量叠在一起，无法单独归因：

1. `UnityPlayer.dll` 被 VMProtect 加壳，导入解析过程不可观察；
2. `NarakaBladepoint.exe` 被 VMProtect 处理，主镜像 `delayImportRVA = 0x0`（延迟导入表被抹）；
3. Neac/ACE 常驻，注入路线本身被阻断。

夹具把 (1) 抽出来，用同样的渲染工作负载，只改「如何解析 `D3D11CreateDevice`」这一个变量。

## 2. 三种解析路径

`artifacts/naraka-fixture/naraka_fixture.cpp`，同一份代码，`-resolve=` 切换：

| 模式 | 做法 | 模拟的现实 |
|---|---|---|
| `import` | 通过 PE 导入表调用（`D3D11CreateDevice` 直接出现在 IAT） | 普通程序 |
| `dynamic` | `LoadLibraryA("d3d11.dll")` + `GetProcAddress` | Unity 常规动态加载 |
| `manual` | `LoadLibraryA` 之后**自己走导出目录**（`AddressOfNames` / `AddressOfNameOrdinals` / `AddressOfFunctions`），全程不碰 `GetProcAddress` | **VMProtect 式自解析** |

渲染负载是游戏形态的六段管线，带 `ID3DUserDefinedAnnotation` 命名，便于事件浏览器识别：

```
ShadowPass(深度) → GBufferPass(双 RT) → AlbedoTintCS(Compute) → LightingPass(全屏)
→ BloomPass(1/4 分辨率) → CompositeUI(混合 UI)
```

夹具通过 RenderDoc 应用层 API（本分支导出的名字是 `TINECMATOOL_GetAPI`，不是
`RENDERDOC_GetAPI`）在第 4 帧自动 `TriggerCapture()`，**不需要按 F12**，因此可无人值守运行。

## 3. 结果矩阵

`run-matrix.py`，每种模式独立输出目录，10 帧，第 4 帧抓帧：

| 模式 | `Graphics function resolved` | 设备进入包装 | `first present` | 产出 .rdc |
|---|---|---|---|---|
| `import` | —（静态导入不需要） | **是** | **是** | 0.82 MB |
| `dynamic` | **1 次** | **是** | **是** | 0.82 MB |
| **`manual`** | **0 次** | **否** | **否** | **无**，`captures recorded: 0` |

三种模式下 `Loading into` 与 `Registering D3D11 hooks` 都正常出现，`IAT slot patched` 都是 6 次——
说明钩子安装环节没问题，**差别只在目标怎么取函数地址**。

`manual` 的日志签名与 Naraka 01:14 那次**完全一致**：

```
Graphics function resolved  : 0
created wrapped device      : 无
Graphics first present      : 无
```

## 3.5 D3D12 对照（同一套结论）

`naraka_fixture12.cpp`，同样的三条解析路径，负载换成 D3D12：GBuffer 双 RT 两笔 draw + 合成一笔，
交换链走 `IDXGIFactory2::CreateSwapChainForHwnd(queue, ...)`。

| 模式 | `Graphics device returned` | 队列包装 | 设备包装 | `first present` | 产出 .rdc |
|---|---|---|---|---|---|
| `import` | 是 | 是 | 是 | 是 | 4.06 MB |
| `dynamic` | 是 | 是 | 是 | 是 | 4.06 MB |
| **`manual`** | **无** | **无** | **否** | **否** | **无** |

与 D3D11 完全同构。也就是说这个漏点与 API 无关：**任何自解析导出的目标都看不到我们的钩子**，
D3D12 侧同样如此（DF 能在 DF 客户端上抓到，是因为 DF 走的是延迟导入 + 被 `ProcessMainDelayImports`
接管的那条路，不是自解析路径）。

两点补充：

- **M4 工厂桥没有被触发**（三种模式都没有 `Graphics native factory bridge installed`）。因为夹具用的是
  被钩住的 factory 直接建交换链；DF 那个 `E_NOINTERFACE` 发生在游戏从适配器 `GetParent` 拿到
  **原生** factory 之后。要覆盖 M4，夹具需要增加一个 `-factory=native` 模式，作为下一步。
- D3D12 夹具的 compute PSO 在本机驱动上返回 `E_INVALIDARG`（根签名与 bytecode 均已验证有效），
  所以 D3D12 版只覆盖 graphics；**dispatch 覆盖留在 D3D11 夹具**。

## 4. 结论

### 4.1 D3D11 之谜解开了

`RegisterFunctionHook` 只做两件事：记录真实函数指针（`hook.orig = GetProcAddress(...)`），
然后改写**其它模块的导入表**。它既不打 d3d11.dll 的导出存根，也不拦截 PE 导出目录遍历。
所以：

- 走 IAT → 被改写的槽位命中 → 包装成功；
- 走 `GetProcAddress` → 被 kernel32 钩子看到 → 记录 `Graphics function resolved` → 包装成功；
- **走导出表自解析 → 两条路都不经过 → 完全不可见。**

VMProtect 在 `UnityPlayer.dll` 里做的正是第三种。这就解释了为什么 01:14 那次
「钩子全装上、`Graphics call entered` 一次没有、设备始终空白」。

### 4.2 但修这个不会解锁 Naraka

即使给 D3D11 补一层导出存根 inline hook，Naraka 仍然抓不到——因为**注入路线本身被挡**：

- 经 `StartGame.exe`（反作弊引导环节）注入 → `NeacClient.exe` 报 `Initialization error 4`，链路停住（见
  `naraka_capture_verified_2026-10-24.json`）；
- 绕开它直启游戏 → 判「启动不合法」，进程 30 秒退出。

也就是说，夹具证明了「技术细节层面到底哪一环漏了」，同时也说明这一环并不是当前的瓶颈。
补 hook 只对**有授权的目标**（自有程序、厂商提供的无 AC 构建）才有意义。

### 4.3 夹具本身的价值

- **回归基线**：任何改动 `win32_hook.cpp` / 钩子注册逻辑之后，跑一次 `run-matrix.py` 就能确认
  `import` 与 `dynamic` 两条路没退化，`manual` 仍然符合预期。
- **可审计的攻防演练**：这正是 `DF_AUTHORIZED_CAPTURE_RESEARCH.md` 里「自建夹具替代方案」要求的形态——
  用自有程序复现失败场景，不触碰任何真实反作弊系统。
- **可扩展**：再加 `-api=d3d12` 就能覆盖 DF 那条 M3/M4 路径；再加一个「N 帧后把 IAT 槽写回原值」
  的模式，就能复现「钩子被后置覆盖」这一类失效。

## 5. 复现步骤

```bat
cd "C:\Program Files\GraphicsDebugger-Naraka\artifacts\naraka-fixture"
build-fixture.cmd

rem 裸跑（不加载工具，验证夹具本身）
naraka_fixture.exe -resolve=import -frames=3
naraka_fixture12.exe -resolve=import -frames=3

rem 全矩阵（D3D11 + D3D12 各三组，需要管理员）
python run-matrix.py

rem 只跑某一组
python run-matrix.py --api=d3d12 manual
```

产物落在 `%LOCALAPPDATA%\Temp\Naraka\fixture-tests\<api>\<mode>\`，
运行日志落在夹具目录的 `fixture.log` / `fixture12.log`。

### 5.1 两个实现细节（踩过）

- **参数用单横线**：`renderdoccmd` 的参数解析器只对 `--` 做特殊处理（当分隔符或
  `--opt=value`），`--resolve=x` 不会落到 `rest()` 里转发给目标；`-resolve=x` 才可以。
- **`printf` 会丢**：由工具拉起时目标进程没有可用 stdout 句柄，`printf` 静默失败。
  夹具因此同时写 `fixture.log`，harness 读文件而不是读管道。

### 5.2 退出码

`TinecmaToolcmd` 报 `0xC0000409`（3221226505）是本机 RenderDoc 收尾时的正常现象，
三种模式都一样，**包括两次成功抓帧的运行**，与抓帧成败无关。判据只看 `.rdc` 是否生成与日志关键行。
