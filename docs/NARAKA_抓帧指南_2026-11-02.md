## 1. 最终方案一句话

**注入渲染进程，然后改图形 DLL 的导出表**——不改游戏文件、不往安装目录放东西、不改任何
机器码。设备创建请求从系统 DLL 的导出入口被转到我们的钩子，于是 RenderDoc 能在设备
创建那一刻把它包装起来。

三个动作，缺一不可：

| 步骤 | 做什么 | 为什么必须 |
|---|---|---|
| ① 注入渲染进程 | 把 `TinecmaTool.dll` 塞进 `NarakaBladepoint.exe` / `...Mobile.exe` | 不注入就没有任何东西在进程里 |
| ② 重定向导出表 | 把 `d3d12!D3D12CreateDevice` 等 6 条 RVA 指向跳板 | IAT 钩子在这游戏上抓不到（§2.3），只有导出表是必经之路 |
| ③ PEB 断链 | 把自己从模块链表摘掉 | 模组枚举看不到我们 |

## 2. 为什么是这条路：四条死路

按时间顺序，每条都是实机测出来的，不是推测。

### 2.1 注入 `StartGame.exe` —— 阻断 Neac（2026-10-24）

注入成功，但 `NeacClient` 不再初始化，游戏进不去。这条 10-24 就判了
`unsupported-protected`。详见旧文档 §9。

### 2.2 同目录代理 DLL —— 被反作弊看见（2026-11-02 17:24）

把 `dxgi.dll` / `d3d11.dll` / `d3d12.dll` 放进游戏目录，让游戏自己加载。**技术链路
全通**，本分支第一次把设备拿进包装：

```
BRIDGE CreateDXGIFactory   -> S_OK
BRIDGE D3D12CreateDevice   -> S_OK level=0xC000
d3d12_hooks.cpp: created wrapped device.
d3d11_hooks.cpp: created wrapped device.        <- D3D11On12
dxgi_wrapped.cpp: Graphics first present: swapchain=... window=...
```

但进游戏时**弹出反作弊提示**，随后游戏拆除图形设备退出，零 `.rdc`。
失败点不是抓帧机制，是「安装目录里多了三个 DLL」这件事被看见。该路线停止，部署脚本
已删除。

### 2.3 IAT 钩子 —— 被 VMProtect 绕开（2026-11-02 18:16）

注入抢在设备创建前 1.1 秒完成，装了 16 个 IAT 钩子，结果：

| 指标 | 值 |
|---|---|
| `Graphics IAT hook installed` | 16 |
| `Graphics function resolved` | **0** |
| `created wrapped device` | **0** |

16 个钩子全落在第三方模块（`fidelityfx_*` / `opencv_world490` / `GPUINFO` /
`sl.common` / `d3d11on12` / `libxess_fg` / `nvwgf2umx`）。真正做设备创建的
`UnityPlayer_LVB.dll` 只钩上了 `dxgi!CreateDXGIFactory`，它的
`kernel32!GetProcAddress` 槽位根本没出现在日志里——VMProtect 保护的解析路径绕开了 IAT。

**重要副产品：注入本身没有被检测。** DLL 加载、16 次 IAT 写入、游戏正常跑完，无提示、
无崩溃记录。所以"注入"不是被封的原因，卡点是解析路径。

### 2.4 函数入口 inline hook —— 评估后放弃

理论上可行：直接改 `System32\d3d11.dll` 里函数前 16 字节，跳到 trampoline。但它要写
**代码页**，而反作弊的完整性校验正是冲这个来的，检测风险比"安装目录多三个文件"更高。
没有做。§1 的导出表方案是不碰代码页的替代品。

## 3. 实现要点

### 3.1 导出表重定向

`LibraryHooks::RedirectExport()`（`renderdoc/os/win32/win32_hook.cpp`）：

- 在模块**节的尾部空隙**里找 12 字节全零区（加载器映射 `SizeOfRawData`，其中只有
  `VirtualSize` 是有效内容，其余是补零；实测 dxgi 每节 1.2–4 KB 连续零）
- 写跳板 `mov rax, imm64 ; jmp rax`
- 把 `AddressOfFunctions[ordinal]` 改成跳板的新 RVA
- 只对那 12 字节和导出表项 4 字节 `VirtualProtect`，写完立即恢复

**跳板必须放在模块自己的镜像内**：RVA 只能在模块基址之上偏移，放到我们 DLL 里通常
超出 32 位范围。

覆盖 6 条：`d3d12!D3D12CreateDevice`、`d3d11!D3D11CreateDevice`、
`d3d11!D3D11CreateDeviceAndSwapChain`、`dxgi!CreateDXGIFactory` / `1` / `2`。

### 3.2 两个配套机制

**原始指针缓存。** 导出表一改，`GetProcAddress(d3d12, "D3D12CreateDevice")` 返回的就是
我们的钩子。钩子再去"找真实函数"会调回自己 → 无限递归（和代理那次同症状）。
所以重定向时把原始地址存进 `GetExportOriginal()`，三处钩子统一按
**缓存 → HookedFunction → GetProcAddress** 的顺序解析。

**延迟到模块加载那一刻。** 注入发生在游戏启动 1 秒时，那时 `dxgi`/`d3d11`/`d3d12`
还没加载，直接改会全部 `not loaded`。轮询也不够——调用方 `LoadLibrary` 返回后**立刻**
解析并保存指针，晚 100 毫秒改的就是没人再读的那条记录了。
改用 `LdrRegisterDllNotification`：模块**正在映射、尚未返回给调用方**时触发回调，
顺序变成

```
模块映射 → 改导出 → LoadLibrary 返回 → 调用方解析 → 拿到我们的钩子
```

### 3.3 PEB 断链

`RegisterHooks()` 完成后把自己从 PEB 的三条模块链表里摘掉
（`win32_libentry.cpp`）。`TCM_NO_PEB_UNLINK=1` 可关闭（调试用），x86 平台自动跳过
（PEB 在 `fs:[0x30]`，布局不同）。

### 3.4 抓帧触发

有两条路，**优先用热键**。

**① 热键（默认可用，不需要重编核心）**

`core.cpp:615-617` 里默认就设了捕获键：

```cpp
m_CaptureKeys.clear();
m_CaptureKeys.push_back(eRENDERDOC_Key_F12);
m_CaptureKeys.push_back(eRENDERDOC_Key_PrtScrn);
```

`RenderDoc::Tick()` 在每次 Present 里检查这些键（`d3d11_device.cpp:2724` 等），按下即
`TriggerCapture(1)`。

**但游戏窗口必须在前台**（`win32_stringio.cpp:141-160`）：先 `GetAsyncKeyState` 读全局
按键，再拿 `GetForegroundWindow()` 和我们登记的窗口（含父窗口链）比对，不在前台就
`return false`。所以顺序是：**先点一下游戏窗口 → 再按 F12**。用脚本发按键时也必须先
`SetForegroundWindow`，否则按了等于没按（2026-11-03 02:02 实测：不聚焦按 F12 无反应，
聚焦后同一秒就抓到帧）。

> 本文早期版本写过"RenderDoc 没有内置热键"，**那是错的**——当时只看到注入场景下没人调
> `TriggerCapture`，没注意到 Tick 里的按键检查。

**② 触发文件（需要重编核心）**

核心另带一个监视线程（`5c2c7436c`），轮询下面这个文件，出现即抓帧：

```
%LOCALAPPDATA%\Temp\Naraka\proxy\captures\trigger_capture_narakabladepoint
```

目录名里的 `proxy` 是历史遗留，**核心自己解析这个路径**，改名会直接断掉，所以保留。

该线程与代理路线用的监视线程互斥（靠 `g_SkipGraphicsDriverHooks` 区分），不会抢同一次
抓帧。**当前 `TinecmaTool.dll` 不含这个线程**，所以文件触发暂时无效，用 F12。

## 4. 怎么用

### 4.1 图形界面（正常用法）

```
tools\naraka\Naraka-Launcher.bat      双击
```

在「1. 目标」里选 PC 或手游（切换后路径框和状态区会跟着变）→ 启动游戏 → 自动打开
`qTinecmaTool.exe` → 等渲染进程出现即注入 → 状态变「就绪」后按「抓帧」。

### 4.2 命令行

```
tools\naraka\run-naraka.bat          启动游戏，只观察
tools\naraka\run-naraka.bat inject   启动 + 注入（抓帧走这个）
tools\naraka\run-naraka.bat capture  写触发文件，等 .rdc 落盘
tools\naraka\run-naraka.bat tool     只打开分析器
tools\naraka\run-naraka.bat status   环境自检，什么都不启动
```

每个模式都可以带目标作第二个参数，或者直接把目标当第一个参数：

```
run-naraka.bat inject mobile     # 手游，注入并等设备
run-naraka.bat status mobile     # 手游，只看环境
run-naraka.bat mobile            # 等价于 inject mobile
```

### 4.3 手游的完整步骤（和 PC 不一样，照这个走）

手游**不能直接起 `StartGame_l22.exe`**（三种方式都秒退，详见 §0），必须让启动器把上下文
发下来。顺序是固定的：

1. 开启动器 `F:\NarakaMobile\NGP\NarakaMobileLauncher.exe`（**不要提权**，见 §7.1）
2. 等它到主界面，看到「启动游戏」按钮
3. **先把注入等待挂上**，再点按钮（顺序反了会来不及——渲染进程出现后十几秒就创建设备）

   ```
   tools\naraka\run-naraka.bat inject mobile
   ```

   它自己那次 `StartGame_l22` 会秒退，无所谓；关键接着的 100ms 轮询会抓到启动器拉起来的
   渲染进程并立刻注入。
4. 点「启动游戏」
5. 日志里等 `created wrapped device`（`%LOCALAPPDATA%\Temp\TinecmaTool\RenderDoc_app_*.log`）
6. 进到要抓的画面，**点一下游戏窗口**（窗口标题 `NarakaMobile`），再按 **F12**
7. 产物在 `%LOCALAPPDATA%\Temp\TinecmaTool\NarakaBladepointMobile_<date>_frame<N>.rdc`

第 6 步的前台要求不是可选的：`GetKeyState` 会比对 `GetForegroundWindow()`，不聚焦就
`return false`（§3.4）。实测不聚焦按 F12 毫无反应，聚焦后同一秒就出帧。

> 全程不需要改游戏目录、不需要重编核心。

## 6. 排查表

| 症状 | 先看什么 | 结论 |
|---|---|---|
| 游戏根本不起，`NeacClient` 起了但无主进程 | 启动它的父进程是否提权 | 必须中等完整性；经 `explorer.exe` 拉起 |
| 分析器窗口闪一下就没了 | 同上 | Qt 窗口在提权进程里也会自退 |
| 注入报失败 | `Failed to inject` 之后是否有 `Loading into ...` | 工具有假退出码，看日志才算 |
| 有 `Export redirect` 但少于 6 条 | 少了哪几个模块 | `not loaded` = 注入早于模块加载；`no usable padding` = 找不到空隙 |
| 完全没有 `Export redirect` | `LdrRegisterDllNotification` 是否注册成功 | 见 §7.3 |
| 6 条齐了仍无 `wrapped device` | 调用方是否走 `GetProcAddress` | 若走手爬导出表也不会命中，需要更深的手段 |
| 有 `wrapped device` 无 `first present` | 游戏是否真的进了 3D 画面 | 加载画面/登录界面不呈现 |
| 触发文件写了没有 `.rdc` | 核心是否含触发线程 | 没重编就用 **F12**（默认捕获键，见 §3.4） |
| 单帧 2.2 GB 偏大 | 抓帧设置里的「保存全部缓冲区」「引用所有资源」 | 收紧可降一半以上 |

## 7. 六个必须记住的坑

### 7.1 提权 = 游戏不起（也 = 分析器退出）

从高完整性会话 `Start-Process` 拉 `StartGame.exe`：`NeacClient` 起，但
`NarakaBladepoint.exe` 永不出现、`Player.log` 不更新。经 `explorer.exe`（中等完整性）
拉起则正常。`qTinecmaTool.exe` 同样——提权启动时窗口起来几秒就自己消失，日志停在驱动
枚举完成那行，事件日志无崩溃记录。

**排查"没起来"先看父进程完整性。**

### 7.2 时序窗口

渲染进程约在 `StartGame` 之后 **8–12 秒**出现，设备在其后 **十几秒**才创建。
19:08 那次的实测：`StartGame` 19:08:30 → 渲染进程 19:08:38 → `wrapped device`
19:08:54 → `first present` 19:08:57。

错过就这一局没救——RenderDoc 只能包装它亲眼看到创建的那个设备。批处理的
`tasklist` + `ping` 光发现进程就要 10 秒，所以等待放在 `wait-and-inject.ps1` 里单进程
100ms 轮询。

### 7.3 `LDR_DLL_NOTIFICATION_DATA` 里边还有一层 `Flags`

结构是「`Flags` + 联合体」，而联合体里的 `LDR_DLL_LOADED_NOTIFICATION_DATA`
**自己开头还有一个保留 `Flags`**。漏掉它，后面所有指针偏移 8 字节：`BaseDllName`
实际读到 `FullDllName`（完整路径），比较永远不相等——回调照常执行、什么也没做、什么都
不报。没有崩溃，这是最难查的一种。

### 7.4 `getenv` 看不见 `SetEnvironmentVariable`

CRT 启动时对环境做快照。代理要在加载核心前设 `TCM_SKIP_GRAPHICS_IAT`，核心侧必须用
`GetEnvironmentVariableA` 读，`getenv` 读到的是旧值。

### 7.5 通用转发器的参数个数取最宽

`D3D11On12CreateDevice` 有 **10 个参数**（NVIDIA Aftermath 在用）。转发器只声明 6 个
时，第 7–10 个是栈上垃圾 → 真 d3d11 里解引用崩溃
（`0xC0000005 @ System32\d3d11.dll + 0xAC321`）。x64 下**多传无害、少传致命**，统一为
12 个。

### 7.6 `TinecmaToolcmd` 的退出码不能当判据

`version` / `--help` / `thumb` **全部**返回非零（管道里 127，CreateProcess 里
`0xC0000409`）。判成功只能看 stdout 内容 + 产物文件。
